# Audit Integrity Operations

## Purpose

The platform protects `AuditEvent` history with a tenant-scoped (and global-scope) HMAC-SHA256 hash chain. Each event records a monotonically increasing `chain_sequence`, the preceding event hash, the HMAC of its canonical immutable snapshot, and an `integrity_key_id`. `AuditChainState` stores the expected sequence and hash at the current chain head.

This control is **tamper-evident**, not tamper-proof. It is one repository-side layer in the audit security model and does not replace database least privilege, protected backups, external immutable/WORM storage, or independent security validation.

## Production key custody

Production deployments must set both:

```text
AUDIT_INTEGRITY_KEY=<at least 32 random bytes, preferably generated by an approved CSPRNG>
AUDIT_INTEGRITY_KEY_ID=v1
```

`APP_ENV=production` fails closed if `AUDIT_INTEGRITY_KEY` is absent. Development and CI may fall back to `DJANGO_SECRET_KEY` for testability only.

Operational requirements:

- Keep the audit key separate from `DJANGO_SECRET_KEY` and database credentials.
- Do not commit the key to Git, images, compose files, support bundles, tickets, or ordinary application backups.
- Inject it through the approved deployment secret mechanism or protected environment boundary.
- Maintain protected recovery material so a restored database can still be verified.
- Restrict key access to the smallest operational role set possible and record access/rotation events outside the application database where practical.
- A database administrator who can alter rows but cannot access the key should not be able to recompute valid event HMACs.

## Key rotation constraint

The current implementation supports one active integrity key ID at runtime. Events retain their `integrity_key_id`, but the verifier intentionally fails with `integrity_key_unavailable` if an event references a key ID that is not the active deployment key.

Therefore **do not rotate by simply replacing `AUDIT_INTEGRITY_KEY` / `AUDIT_INTEGRITY_KEY_ID` in place**. A production rotation requires one of the following controlled changes:

1. introduce an approved historical-key/keyring mechanism and retain prior key material for verification; or
2. perform a documented full-history reseal under maintenance controls, preserve pre-reseal evidence externally, and update the chain heads atomically.

Until one of those procedures is implemented and approved, treat the audit integrity key as long-lived recovery-sensitive material.

## Historical sealing migration

Migration `audit.0005_seal_existing_audit_history` seals audit records that existed before the integrity chain was introduced. It deliberately reseals the complete current history of every scope, not only rows with `chain_sequence=0`.

For each tenant/global scope the migration:

1. temporarily neutralizes chain fields inside the migration transaction so existing positive sequence values cannot collide with the conditional uniqueness constraints;
2. orders events deterministically by `created_at`, then `id`;
3. assigns a contiguous sequence starting at 1;
4. links each event to the preceding event hash, beginning at the genesis hash (`64` zeroes);
5. computes HMAC-SHA256 over the canonical `grc-audit-chain-v1` payload; and
6. updates `AuditChainState` to the resulting head.

The migration is atomic on the supported PostgreSQL deployment path. Its reverse operation intentionally leaves the sealed data in place because schema/application version `0004` can consume the sealed fields and unsealing would weaken integrity. This makes rollback application-compatible without destroying the new security evidence.

If events were created after `0004` but before `0005`, they are resealed together with legacy records so the resulting scope is one contiguous deterministic chain. Consequently, pre-`0005` hashes must not be treated as permanent external anchors.

## Verification command

Verify all known tenant/global scopes:

```bash
python manage.py verify_audit_integrity --json
```

Verify one tenant:

```bash
python manage.py verify_audit_integrity --tenant-id <tenant-uuid> --json
```

Verify only the global scope:

```bash
python manage.py verify_audit_integrity --global-scope --json
```

The JSON output uses schema `grc-audit-integrity-report-v1`. The command exits non-zero when any scope fails verification.

Findings include:

- `sequence_mismatch` — missing/duplicated/out-of-order chain sequence;
- `unsealed_event` — required integrity metadata is missing;
- `previous_hash_mismatch` — the stored predecessor link is inconsistent;
- `event_hash_mismatch` — event content no longer matches its HMAC;
- `integrity_key_unavailable` — the key ID needed to verify an event is not available;
- `chain_state_missing` — events exist without a chain-head state row;
- `chain_state_scope_mismatch` — a head row points at the wrong tenant scope;
- `chain_head_sequence_mismatch` / `chain_head_hash_mismatch` — the stored head does not match the final stored event.

Preserve failed reports as incident/security evidence before attempting remediation.

## Verification cadence

At minimum, run verification:

- immediately after the `0005` migration or any future history reseal;
- after every database restore or disaster-recovery exercise;
- after any audit-table maintenance or privileged database intervention;
- before generating security/audit evidence intended for external reliance;
- during incident response when audit history is relevant; and
- on a recurring operational schedule (recommended daily for the pilot/production baseline).

Store recurring verification reports outside the mutable application database. For stronger evidence, send signed/dated reports or audit exports to an approved immutable/WORM destination or equivalent protected evidence repository.

## Backup and recovery

A usable audit-integrity recovery set includes:

- the database backup;
- the matching `AUDIT_INTEGRITY_KEY` and `AUDIT_INTEGRITY_KEY_ID` recovery material held under separate protection; and
- preferably an external prior verification report or chain-head checkpoint.

After restore:

1. restore the database using the normal approved recovery procedure;
2. restore/inject the matching audit integrity key separately;
3. run `verify_audit_integrity --json` before treating restored audit history as trusted;
4. preserve the resulting report with the recovery evidence; and
5. investigate any mismatch before normal service resumes where audit assurance is required.

Do not put the audit integrity key inside ordinary support-evidence bundles.

## Security boundaries and known limitations

The HMAC chain detects many database-only mutations while the key remains separately protected, including event content changes, middle-of-chain deletion/gaps, broken predecessor links, and chain-head drift.

It does **not** provide complete immutability:

- An attacker who compromises both the database and the integrity key can recompute history.
- A database-only attacker can potentially truncate the end of a chain and move the mutable `AuditChainState` backward to the last retained valid event without computing a new HMAC. Detecting that class of rollback requires an externally protected prior head/checkpoint or immutable/WORM copy.
- Application-level append-only guards do not stop a privileged database operator from issuing raw SQL.
- HMAC verification does not prove that an event was truthful when originally recorded; it protects the recorded snapshot from undetected modification under the stated key boundary.
- The chain does not replace database access controls, backup protections, SIEM/export controls, or independent penetration/security acceptance tracked elsewhere (including #8).

For these reasons, deployment acceptance still requires least-privilege database access, protected backup/recovery, operational verification evidence, and an approved external immutability/checkpoint strategy where the assurance level demands it.
